# Глубокие логи обмена с ЭБУ

Задача скилла — получить ПОЛНЫЙ, таймстемпованный, воспроизводимый лог обмена: свой (активный клиент) или чужой (перехват программы). Правило: лог обязан быть пригоден для механического разбора — сырые байты, направления, времена, конфигурация сессии, ошибки.

## Шаг 1 — Выбери уровень перехвата

| Уровень | Что видно | Когда выбирать | Инструменты |
|---|---|---|---|
| Шина (аналог/логика) | фронты, 5-baud init, тайминги, эхо | понять физику, битые кадры, чужие адаптеры | логический анализатор, MCU-сниффер |
| USB (UBR) | bulk-пакеты FTDI | драйвер есть, но API-хук невозможен | USBPcap+Wireshark, Bus Hound |
| Драйвер FTDI (D2XX) | байты + статус, настройки порта | чужая программа ходит через ftd2xx.dll | прокси FTD2XX.DLL |
| ОС (VCP/COM) | ReadFile/WriteFile | программа ходит через COM-порт | Frida-хуки, com0com, наших скрипт |
| Устройство (J2534) | PASSTHRU_MSG, ошибки шины | чужое ПО ходит через Pass-Thru API | прокси J2534 (см. capture-layers.md) |
| Приложение (EDIABAS) | джобы, телеграммы, поля | программа — из мира EDIABAS (INPA/WinKFP) | штатные трассы `ifh.trc`/`api.trc` |

Порядок предпочтения для «снять с чужой программы»: **штатные трассы программы → API-хуки (Frida) → прокси DLL драйвера → USB → анализатор**. Каждый следующий уровень глубже, но дороже.

## Шаг 2 — Свой логгер (активный)

Готовый скрипт: `scripts/ftdi_kline_logger.py` (Python, D2XX через пакет `ftd2xx` или VCP через `pyserial`).

```bash
# пассивно слушать K-line на FT232R (9600, DS2)
python ftdi_kline_logger.py --serial A1B2C3D4 --baud 9600 --parity even --latency 1 --listen --out ds2-listen.jsonl

# DS2-идентификация блока + ответы (запрос "12 04 00 16")
python ftdi_kline_logger.py --serial A1B2C3D4 --ladder 125000,19200,9600 --probe-ds2 --out ident.log

# повторить захваченную сессию (реплей для проверки клиента)
python ftdi_kline_logger.py --serial A1B2C3D4 --replay work/orig-capture/winkfp-session-trace.txt --from 0 --to 40 --out replay.log

# самопроверка кода без железа
python ftdi_kline_logger.py --selftest
```

Ключевые настройки активного логгера (обоснование — `references/ftdi-d2xx.md`):
1. Открывать **по серийнику** (`--serial`), не по индексу.
2. **Latency timer = 1 мс**, таймауты 1000–3000 мс, `FT_Purge` до сессии.
3. Порядок настройки: open → reset → timeouts → latency → baud → data characteristics → flow control off → purge.
4. **Скорости нестандартные** для FTDI — норма (таблица делителей в ftdi-d2xx.md): 9600/10400/19200 точные, 125000 точная.
5. **Эхо обязательно** на K-line: после записи прочитать ровно `len` отправленных байт; первое расхождение — уже ответ ЭБУ; адаптеры без эха определяются по «нулю прочитанных байт».
6. DS2-мир: модель оригинала — **лестница скоростей** 125000 → 19200 → 9600, по одной попытке на скорость, ретраи — только на последней; успех = ответ `A0`.

Почему не «просто pyserial»: `pyserial` по умолчанию получает latency 16 мс, не умеет bit-bang и 5 бод. Для быстрого VCP-зацепа он годится (см. ниже), для глубокого лога — D2XX.

## Шаг 3 — Снять с чужой программы

### 3.1 Штатные трассы (самый дешёвый и точный путь)
- **EDIABAS/WinKFP/INPA**: включить `ApiTrace`/`IfhTrace` в `C:\EDIABAS\BIN\EDIABAS.INI`, снять `C:\EDIABAS\TRACE\ifh.trc` — там ЯВНЫЕ телеграммы INPUT/OUTPUT с миллисекундными метками. Полный рецепт — `protocol-reference/references/ediabas.md`.
- Любая программа, умеющая писать protocol-trace (J2534 Toolbox, ODIS и т.п.) — ищи опцию «trace/log/session log» в первую очередь.

### 3.2 Frida — хуки COM-порта (`scripts/frida-serial-hook.js`)
Перехватывает `CreateFileW/ReadFile/WriteFile/CloseHandle` (kernel32 и kernelbase!) по COM-хендлам, плюс экспорты `ftd2xx.dll`, если он загружен. Запуск:

```bash
frida -f "C:\path\app.exe" -l frida-serial-hook.js -o capture-live.log
# или attach к уже запущенной:
python frida-launch.py --attach 12345 --out capture-live.log
```
Таймстемпы относительные (`[+94.086s]`), сырые байты, отметки rc/n. Подводные камни (overlapped I/O, kernelbase, Frida 17 API) — в `references/capture-layers.md`.

### 3.3 Прокси-DLL для ftd2xx.dll (`scripts/ftd2xx_proxy/`)
Оригинал переименовать в `FTD2XX_orig.dll`, рядом положить нашу `FTD2XX.DLL` с теми же экспортами: обёрнутые функции логируют и вызывают оригинал, остальные — форвардятся через `.def`. Сборка и внедрение — в README каталога. Формат лога совместим с Frida-логгером.

### 3.4 Прокси J2534 (`scripts/j2534_proxy/`)
Для Pass-Thru ПО: подменить путь `Function Library` в реестре (`HKLM\SOFTWARE\WOW6432Node\PassThruSupport.04.04\<Vendor>`) на свою 32-битную DLL; логируются все `PassThru*` вызовы и дампы `PASSTHRU_MSG`. Детали и открытые проекты-аналоги — `references/capture-layers.md`.

### 3.5 USB и шина
- `USBPcapCMD.exe -d \\.\USBPcap2 -o - | Wireshark.exe -k -i -` — Wireshark с версии 3.2 понимает FTDI (dissector `ftdi-ft`, 2-байтный заголовок статуса).
- Bus Hound — быстрый GUI-монитор USB.
- Логический анализатор: **два канала** (K-линия через делитель + RX-выход трансивера) — сразу видно, что эхо, а что ответ; UART-декодер 10400 8N1; 5-baud init читается глазами по фронтам.

## Шаг 4 — Зафиксируй лог по канону

Формат, поля, шапка, регекспы парсинга — `references/log-format.md`. Кратко: шапка с конфигурацией → поток строк `[+t] DIR SRC bytes` → эпилог со счётчиками. Плюс опциональный JSONL-дубль для машинного разбора. **Не парси обмен во время захвата** — только фиксируй.

## Шаг 5 — Чек-лист качества лога

- [ ] В шапке: дата/время (wall-clock), адаптер (серийник/описание), драйвер (D2XX/VCP + версия), порт, скорость, чётность, latency, целевой софт и его версия.
- [ ] Таймстемпы монотонные, с миллисекундами; отдельно якорь wall-clock.
- [ ] Каждое направление помечено (TX/RX/VCP/FT/EHО-mark); эхо отмечено явно.
- [ ] Ошибки зафиксированы (frame/parity/overrun, `<read-error …>`), а не проглочены.
- [ ] Сырые байты без «чистки» и без интерпретации.
- [ ] Для чужого ПО: параллельно сохранён контекст действий человека (что жали, скриншоты состояний).
- [ ] Лог неизменяем: после записи — только чтение (или копия `*-raw.log`).

## Подводные камни (проверено на практике)

- **VCP и D2XX взаимоисключающие**: одну и ту же программу нельзя одновременно слушать через COM и D2XX. Планируй захват заранее.
- `FT_Read` возвращает меньше запрошенного и «кусками» — нельзя резать поток по границам read; нарезка на кадры — только парсером.
- Точность таймстемпов FTDI = latency timer (1 мс) + USB-фрейм (~1 мс). Для пауз P1/P4 это фиксируй в метаданных, иначе тайминги «не защитить» в отчёте.
- 5 бод FTDI не умеет (минимум ~183 бода). Bit-bang через `FT_SetBitMode` возможен, но на Windows точность ~15.6 мс без `timeBeginPeriod(1)`; стабильный 5-baud init — делегируй адаптеру (J2534 `FIVE_BAUD_INIT`, ELM327) или MCU.
- Прокси-DLL обязана совпадать по битности с процессом (32/64) и лежать рядом с EXE или в пути поиска; список экспортов бери `dumpbin /exports`.
- Frida: хукай и `kernel32.dll`, и `kernelbase.dll`; для overlapped I/O логируй в `onLeave`/по завершению, иначе получишь мусор.
- Антивирусы и OneDrive любят мешать: рабочие каталоги для логов — вне синхронизируемых папок.
