# DS2 (BMW) — протокол K-line диагностики и программирования

Статус: ядро формата и таблица команд — **wire-verified** на стендовом BMS46 (Bosch DME M43, E36/E46) через FT232R + EDIABAS 7.3 + собственная реплика (2026-10-11/12). Публичные детали помечены отдельно.

## 1. Физика и кадр

- **K-line 9600 бод, 8E1** (данные 8, чётность EVEN, стоп 1). На E36/E39/E46 диагностическая K-линия сидит на **пине 8** J1962 (не 7) — сторонним адаптерам нужен мостик 7↔8 (`code-grounded/вторичные источники`).
- Кадр: `[ADDR][LEN][PAYLOAD…][CKS]`
  - `ADDR` — адрес ЭБУ (DME = **0x12**; известны 0x32 = GS20 АКПП, 0x80 = приборка);
  - `LEN` — **ПОЛНАЯ длина кадра на линии** (addr + len + payload + cks), допустимо 4..250 (наш клиент валидирует 4..250);
  - `CKS` = **XOR всех байт, кроме самого CKS**.
- Эталон (wire-verified): запрос `12 04 00 16` → ответ `12 2E A0 "14309406100A76050" "98010213510" "F0000001" "11832" 9F`. В запросе: `0x12^0x04^0x00 = 0x16` ✓.
- **Эхо обязательно**: K-line полудуплекс, сырой FT232R возвращает отправленное. Алгоритм: после write прочитать ровно `len` отправленных байт; первое расхождение = начало ответа. Адаптеры без эха определяются по «0 прочитанных байт» — клиент должен уметь оба режима.

## 2. Статусы ответа (payload[0])

| Байт | Значение | Наблюдения |
|---|---|---|
| `0xA0` | OK / данные | `A0` без данных = «принято»; `A0 <данные>` = ответ |
| `0xA1` | Busy | `12 04 0A 1C` во время длинных операций (стирание, прогрев) — повторять |
| `0xA2` | Принято (запись/сервис) | ответ на `07 02` (запись) и др.; у оригинального ПО — «Response 0xA2» |
| `0xB0` | Отказ ECU (read blocked и подобное) | встречается на запрещённые чтения/команды |

## 3. Скорости: лестница оригинала

Оригинальное ПО перебирает скорости «сверху вниз» и остаётся на той, где ЭБУ ответил `A0`: **125000 → 19200 → 9600** (по одной попытке на скорость, ретраи — только на последней). Строки оригинала: «Non 0xA0 response attepting to set 19200 baud», «…9600 baud», «Inkorrect cable latency detected. Set to 1ms?».

Телеграммы смены скорости (публичные/code-grounded; форма `91 00 <делитель> 80 01`): `91 00 25 80 01` (9600), `91 00 4B 00 01` (19200), `91 00 F4 24 01` (62500), `91 01 E8 48 01` (125000). Наш стенд (M43_BMS46, SW F0) отвечает **только на 9600**.

## 4. Команды (wire-verified на BMS46, если не указано иное)

| Операция | Payload | Ответ | Семантика |
|---|---|---|---|
| Идентификация | `00` | `A0` + 42 ASCII | layout: BMW-NR / HW / AI / DIAG-INDEX / BUS-INDEX / KW(год,неделя) / LIEF-NR / SW-NR / PROD-NR |
| DTC: счётчик | `04 00` | `A0 <count> FF FF FF FF` | напр. `A0 0A` = 10 записей |
| DTC: страница | `04 <1+4k>` | `A0 <count>` + 4 записи × 20 Б | запись: `[ORT][ART][HFK][16 env]` |
| DTC: очистка | `05` | `A0` | **внимание: `04 05` в контексте сессии — продолжение страниц, standalone — очистка** (двузначная телеграмма!) |
| Очистка контекстов ошибок | `05 01` | `A0` | таблицы `14`, не адаптации |
| Очистка адаптаций | `43 FF FF` | `A0` | `43 <группа16>` — группы |
| Чтение памяти | `06 <addr32 BE> <len≤0x60>` | `A0` + данные | макс 0x60 байт/кадр (wire-verified); 3-байтные формы существуют (публично) |
| Аналоговый live-блок | `0B 03` | `A0` + ~70 Б | поллинг оригинала |
| Цифровой live-блок | `0B 04` | `A0` + ~70 Б | |
| Теневая копия ошибок | `14 <1+4k>` | `A0` + записи × 22 Б | расширенные записи |
| AIF-дескриптор | `04 0D` | `A0` + 73 Б | содержит указатели региона (0x03FD60, 0x03FD20, 0x01459A…) |
| Синхро EWS | `6D` | `A2` | статус синхронизации |
| Конец диагностики | `9F` | `A0` | |

Публичные команды (вторичные источники, для полноты): `0x0D` — capability/HW query; `0x07` — запись (см. ниже). Команда `0x0A` — **не подтверждена в публичных источниках, но wire-verified у нас**: `0A` = вход/коммит программирующей сессии (см. §5).

## 5. Программирование (flash) — скелет сессии WinKFP, разобранный покадрово

Источник: полная запись сессии WinKFP 3.5.3.1 (EDIABAS → COM6 → тот же FT232R), **2173 обмена**, разобрана в `winkfp-session-trace.txt`; многократно воспроизведена нашей репликой. Статус: **wire-verified**.

```
[prep]    04 0D (AIF) · чтения окна 0x3FD60/0x3FD8E (0x2E) · 04 00 (ID)
[auth]    12 08 90 42 4D 57 04     ← «BMW»-авторизация №1 (ответ = строка ID!)
          12 08 90 9A 9B 9C A3     ← авторизация №2 «включение записи» → A0 00
          12 09 07 0F 03 FD 60 00  ← управление окном (A0)
          чтения верификации · 04 00 · 04 0D · 06 @0x1459D (1 Б)
          12 08 90 42 4D 57 07     ← «BMW»-авторизация фазы
[enter]   12 09 07 0F 00 00 00 00  ← валидация состояния → 01
          12 09 07 06 00 00 00 00  ← СТАРТ сессии программы → ~2.98 с СТИРАНИЕ, потом ответ
[writes]  07 02 <addr24 = КОНЕЦ блока> <len8> <данные…> <cks>
          ответ: 12 0A A0 02 <addr24> <len8> 01 <cks>
          блоки 0x5B/0xE4/0xF6 Б у WinKFP; у нас приняты 0x10/0x20/0x40, 0x60 ИГНОРИРУЕТСЯ
[ctl]     07 02 03 FF FC 04 55 FF AA 00   ← контрольное слово конца региона
[final]   12 09 07 0F 03 00 00 00   ← финальная валидация → 01 (все проверки)
[commit]  12 04 0A 1C ×N (A1 = busy, ждать ~0.5 с) → A0 00 = УСПЕХ
```

- **Без авторизации** `07 0F 00 00 00 00` возвращает `A2`, стирание не запускается. С авторизацией (последовательность `90 42 4D 57 04` → `90 9A 9B 9C A3` → `90 42 4D 57 07`) — работает. Это и было причиной «не стирается» у стороннего ПО (`code-grounded`, проверено на проводе).
- **«Мёртвое окно»**: после `07 06` (и `07 0F 00 80 10 00` для калибровок) ЭБУ стирает целевой блок ~3 с (калибровки ~0.8 с) и только потом отвечает. Кадры, отправленные в окно, эхо возвращают, но НЕ обрабатываются — нужен полный wait (до 9 с), а не «ранний выход по idle».
- **Идемпотентность**: повторы записей безопасны; строгий ACK: `07 02` подтверждается ответом с ТЕМИ ЖЕ addr24/len; без ACK после 4 попыток — ABORT (не продолжать «как получится»).
- **Выход из состояния**: `12 04 0A 1C` до `A0 00`. Незавершённая сессия → **pending** (AIF `00 37 3A`, ID с дырками FF, ответ `A2` на авторизацию записи); цикл питания НЕ лечит — лечится завершённым прогоном WinKFP.
- После `07 0F 00 00 00 00` (вход) мета-области перезаписываются указателями на теневую копию, программа блокируется на чтение — это **штатное промежуточное состояние** WinKFP, не поломка.

## 6. Целостность образов BMS46 (эталон для «своего» ЭБУ)

- **CRC-16 отражённая табличная**: `crc = (crc>>8) ^ TABLE[(crc ^ byte) & 0xFF]`, таблица 256 слов (BE) в образе по **0x3D20**, init = 0.
- Регионы: id01 `[0x0..0x3FFF]` cks@0x3F46; id02 `[0x10000..0x14453]` (отключён); id03 `[0x144D0..0x3755F]` cks@0x37560 (init — CRC предыдущего региона, цепочка); **калибровки `[0x8040..0xFFF9]`, слово CRC на 0xFFFA**.
- Эталонные значения калибровок: заводской блок `2989`, WinKFP-обновление `E0C8`, AKPP `8893`.
- При правке калибровок обязательно пересчитывать CRC, иначе финальная валидация `07 0F`/`0A` отклонит прошивку (`0D`/`04`).

## 7. Что осталось непроверенным (для следующих сессий)

- Команда принудительного стирания отдельно от сессии программы.
- Расширенные статусы (`07 0F …` варианты), EWS-процедуры, `43 <группа>` полностью.
- Полная семантика `ThU=`-состояний (16 состояний) оригинального ПО.
