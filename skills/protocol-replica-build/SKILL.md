# Реплика протокола: от спецификации до прошивки на стенде

Правило: реплика строится «слоями», и каждый слой проверяется отдельно — сначала без железа (симулятор), потом read-only на живом ЭБУ, потом запись в стёртую область, и только потом полный цикл.

## 1. Архитектура (проверена на реальном проекте)

```
Transport (сырые байты: FTDI D2XX / VCP / TCP / ENET)   ← только открыть/закрыть/читать/писать
    ↓ события BytesSent / BytesReceived (на них же — трафик-лог)
ProtocolClient (framing, checksum, echo, strict ACK, ретраи, тайминги)
    ↓ операции: ident / read / write / dtc / flash-этапы
ToolProfile (константы конкретного ЭБУ: адрес, скорости, команды, размеры блоков, адреса ок)
    ↓
Tools / UI (прогресс, этапы, логгер с графиками, профили машин)
```

- Транспорт ничего не знает о протоколе; протокол ничего не знает о UI.
- Профиль ЭБУ (JSON) — чтобы один код работал с семейством блоков (у N55/BMS46-семейства — 16 профилей).
- Симулятор транспорта обязателен: без него ветка записи тестируется только на «живом» блоке (медленно и опасно).

## 2. Правила протокольного клиента (каждое — из реальной поломки)

1. **Эхо-обработка**: после write читать ровно `len` отправленных байт; первое расхождение = начало ответа; 0 прочитанных = адаптер без эха (переключи режим, не ломайся).
2. **Строгий ACK** — ответ должен подтверждать ИМЕННО НАШУ телеграмму (sub-команду, addr, len), а не быть «любым непустым ответом»:
   ```csharp
   // эталон (из рабочего проекта): для 07 02 ответ обязан вернуть тот же addr24/len
   if (tg.Length >= 8 && tg[2] == 0x07 && tg[3] == 0x02)
       return r.Length >= 9 && r[3] == 0x02
           && r[4] == tg[4] && r[5] == tg[5] && r[6] == tg[6] && r[7] == tg[7];
   ```
3. **Идемпотентные ретраи**: записи повторяются до 4 раз при таймауте; без ACK после 4 попыток — **ABORT** (не продолжать «как получится»: получишь испорченную сессию).
4. **Полный maxWait**: после «старта сессии» (у DS2 — `07 06`, `07 0F`) ЭБУ стирает блок и НЕ отвечает ~1–3 с; ранний выход по «idle» — баг (телеграммы в «мёртвое окно» эхо возвращают, но не обрабатываются). Ждать полный таймаут (9 с для этих команд).
5. **Busy-статусы — не ошибка**: `A1`/`0x21`/`0x78` = «повтори позже» (ждать, не abort'ить).
6. **Одноразовость**: некоторые операции доступны только в свежем цикле питания (у BMS46 — стирание). Проверяй состояние и предупреждай пользователя.
7. **Контроль целостности**: после записи — читать назад и сверять (побайтово + sha256); для образов с CRC регионов — пересчитывать CRC (иначе финальная валидация отклонит).
8. **Логируй каждый ACK** в acceptance-лог: без него невозможно доказать, что сессия прошла «чисто».

## 3. Движок реплея «золотой трассы» (быстрый путь к рабочему флешу)

Когда есть полная записанная сессия чужой программы, реплика может стартовать как реплей-движок:

```
parse golden trace  →  list[telegram] с флагами (write-block / control / finalize…)
replay(from,to):
  для каждой телеграммы:
    отправить → дождаться ACK (строгая проверка + полный maxWait)
    timeout → повторить (≤4) → всё равно нет → ABORT с логом
  подстановка данных: в 07 02-блоки вставить свой образ (не трогая
  all-FF пре-бланки и контрольные слова), пересчитать XOR
verify: чтение ключевых областей + сверка sha256
```

Затем реплей «разбирается» на операции (ident/auth/erase/write/finalize/commit) и превращается в полноценный флеш-конвейер с прогрессом. Именно так родился рабочий флешер BMS46 (см. `references/playbook-bms46.md`).

## 4. Симулятор ЭБУ (обязательный этап)

Готовый: `scripts/ds2_ecu_sim.py` — минимальный DS2-ЭБУ по TCP (ident, чтения, DTC-счётчик, авторизации, commit с busy). Запуск и совместная работа с логгером (транспорт `--tcp`) — в шапке скрипта. Прогони на симуляторе: открытие, эхо, строгий ACK, ретраи, «мёртвое окно» (добавь `--erase-delay-ms`), полный цикл записи — до первого включения железа.

## 5. Гейты безопасности (не пропускать!)

| Гейт | Что проверяется | Как |
|---|---|---|
| 0. Разрешение | владелец разрешил работу с ЭБУ/машиной | явно спросить; на машине — только чтение без особого разрешения |
| 1. Бэкап | полное чтение всех областей, сохранено, sha256 | до любой записи; у BMS46 — 256 КБ |
| 2. Восстановление | известен путь «как вернуть как было» (штатная программа) и он доступен | проверить на стенде ДО записи |
| 3. Read-only | ident/DTC/чтения совпадают с эталоном бит-в-бит | таблица в acceptance-логе |
| 4. Запись в стёртое | идемпотентная запись в область 0xFF + чтение назад | только на стенде |
| 5. Полный цикл | прошивка чужого образа + коммит + чтение назад | только на стенде, с питанием под контролем |

## 6. Приёмка (wire-acceptance)

Артефакты на каждый прогон: `ACCEPTANCE-<блок>-<что>.log`, `replay-<...>.log`, результат чтения назад + sha256.
Критерии успеха формулируются ДО прогона (пример BMS46): финальная валидация `→ 01`, коммит `0A → A0 00`, AIF `01 45 9A`, ID полный, чтение калибровок sha256 = исходный файл.

## 7. Состояния отказа и восстановление

- Признаки «полусессии» (pending): изменились мета-поля (AIF/указатели), ID частично `FF`, отказ `A2` на авторизацию записи. Цикл питания может НЕ помогать (маркер во флеше).
- Восстановление: штатная программа (WinKFP и аналоги). Держи её и конфигурацию под рукой; после восстановления собственный прогон делай в том же цикле питания.
- Никогда не бросай сессию «как есть»: логируй точку останова, чтобы следующая попытка знала состояние.

## 8. UX (если делаешь приложение)

Этапы с прогрессом: соединение → идентификация → авторизация → стирание → запись (по регионам) → верификация → коммит; живой лог кадров; экспорт лога/CSV; профили машин; «сухой прогон» (dry-run) без записи; запрет запуска без бэкапа.
