# Плейбук: BMS46 / DS2 — от нуля до прошивки чужого образа

Реальный кейс (2026-10-11/12): Bosch BMS46 (DME M43, E36/E46 дизель), стенд, FT232R-шнурок, EDIABAS 7.3 + WinKFP. Итог: собственная реализация полностью прошила чужой 256 КБ образ (2171 телеграмма, ноль потерь) и верифицировалась чтением назад (sha256 совпал). Ниже — весь путь и все грабли.

## 1. Стенд и железо

- Блок BMS46 68k, флеш 256 КБ (0x00000–0x3FFFF), две копии (active + shadow).
- Кабель: FTDI (VCP-совместимый K+DCAN, серийник задокументирован).
- Штатная программа восстановления: WinKFP 3.5.3.1 через `C:\EDIABAS\Bin\obd.ini` → `Port=Com6, Hardware=USB`.
- DS2: 9600 8E1, телеграмма `12 <len> <payload> <xor-cks>`, эхо всегда приходит.

## 2. Порядок работ (что делали по шагам)

1. Трассы EDIABAS (эталонные обмены) → формат кадра и таблица команд.
2. Frida-хук COM-порта → полная запись сессии WinKFP (27 557 строк, 2173 обмена) → `winkfp-session-trace.txt` (золотая трасса).
3. Разбор трассы по этапам (prep/auth/enter/writes/ctl/final/commit).
4. HwProbe (свой зонд на D2XX) — проверка гипотез на живом блоке: авторизации, вход, чтения каталога.
5. Реплей-движок: воспроизведение трассы с подстановкой своего образа калибровок + строгие ACK + повторы.
6. Успех: AKPP-образ прошит полностью; чтение назад = sha256 исходного файла.
7. Разбор прошивки (дизасм 68k): обработчики `07`, таблица регионов CRC, статусы валидации.

## 3. Скелет сессии (эталон, по номерам кадров золотой трассы)

```
[0..5]    чтения идентификации (04 0D = AIF, 06 = память)
[6]       12 08 90 42 4D 57 04     авторизация №1 → ответ = строка ID
[7]       12 08 90 9A 9B 9C A3     авторизация №2 (включение записи) → A0 00
[8..25]   чтения + 12 08 90 42 4D 57 07 (авторизация фазы)
[26]      07 0F 00 00 00 00        валидация → 01
[27]      07 06 00 00 00 00        СТАРТ сессии программы → ~2.98 с стирание → ответ
[28..2017] 07 02 <addr24 = КОНЕЦ блока> <len8> <data> → ответ 12 0A A0 02 <addr> <len> 01
[2018]    07 0F 03 00 00 00        конец 1-й загрузки → 01
[2019..2031] чтения AIF (показывают SHADOW — норма!), авторизация, старт калибровочной сессии
[2033..2167] записи калибровок 0x8010..0xFFFC
[2168]    07 02 00 FF FC 04 00 55 FF AA  контрольное слово
[2169]    07 0F 03 00 00 00        ФИНАЛЬНАЯ валидация → 01
[2170+]   12 04 0A 1C ×N          коммит: A1 = busy (ждать ~0.5 с), A0 00 = УСПЕХ
```

Критерий успеха: `[2169] → 01` И `0A → A0 00`; далее AIF `01 45 9A`, полный ID, версии из образа.

## 4. Корневая причина прошлых провалов (главный урок)

После `07 06` ЭБУ стирает блок (~3 с; калибровки ~0.8 с) и только потом отвечает. Реплей слал данные в это «мёртвое окно»: эхо приходило, обработки не было; потеря `[2033]/[2034]` оставляла слоты версий `FF` → финал `0D`; потеря калибровок ломала CRC → коммит `04` → shadow. **Данные образов были корректны — виноваты тайминги.**

Лечение (реализовано в HwProbe `Program.cs`):
1) `IsExpectedAck` — строгая проверка подтверждения (см. SKILL.md §2);
2) таймаут → повтор (записи идемпотентны), ≤4 попыток;
3) нет ACK после 4 → ABORT (exit 3), не продолжать;
4) ждать ПОЛНЫЙ maxWait: 9 с для `07 06`/`07 0F`, 2.5 с иначе; ранний выход по idle — баг.

## 5. Целостность калибровок (CRC)

- Отражённая табличная CRC-16 (init = 0), таблица 256 слов BE по смещению **0x3D20** в образе.
- Регион калибровок **[0x8040..0xFFF9]**, ожидаемое слово на **0xFFFA** (BE).
- Регионы (таблица @0x14204, записи 16 Б: +2 маска, +4 start, +8 end, +12 = адрес указателя на слово cks):
  id01 `[0x0..0x3FFF]` cks@0x3F46; id02 `[0x10000..0x14453]` (отключён); id03 `[0x144D0..0x3755F]` cks@0x37560 (init — цепочка от предыдущего региона); cal `[0x8040..0xFFF9]` cks@0xFFFA.
- Эталоны: завод `2989`, обновление WinKFP `E0C8`, AKPP `8893`, машина 330 `2319`.
- Скрипт проверки/пересчёта: `crc_verify.py` (в проекте). Любая правка калибровок → пересчитать CRC, иначе финал отклонит прошивку.

## 6. Состояния блока и восстановление

- Чистое состояние: AIF `01 45 9A`; pending: AIF `00 37 3A`, ID с дырками `FF`, `A2` на авторизацию записи.
- **Цикл питания pending НЕ лечит** (маркер во флеше). Лечение — завершённый прогон WinKFP; после него работать в том же цикле питания.
- После `07 0F 00 00 00 00` (вход в режим) мета-области перезаписываются указателями на тень, программа блокируется на чтение — это штатное промежуточное состояние; выход — прогон WinKFP или полный цикл прошивки.

## 7. Особенности протокола, найденные эмпирически

- Размер блока записи: приняты `0x10/0x20/0x40`, **`0x60` игнорируется** (хотя чтение — до 0x60).
- `04 05` — очистка ошибок standalone, но «продолжение страницы» внутри сессии чтения.
- Чтение памяти: `06 <addr32 BE> <len≤0x60>`; адреса 0x4000/0x5000 могут отвечать `B0`.
- Лестница скоростей оригинала: 125000 → 19200 → 9600 (по одной попытке, бюджет ретраев — только на последней).

## 8. Acceptance-критерии (как доказывали успех)

- Лог прогона: каждый ACK с addr/len; 0 ошибок; `07 0F → 01`; `0A → A0 00`.
- Чтение назад всей области калибровок + сверка sha256 с исходным файлом (совпало).
- Состояние после: AIF `01 45 9A`, полный ID, версии `01119700F000Q2DG`×3 (для AKPP-образа).
