# Реверс-инжиниринг диагностических протоколов ЭБУ

Ты ведёшь задачу от сырого обмена на проводе до работающей, wire-верифицированной реализации протокола в нашей программе. Работает для EDIABAS-мира (DS2, BMW-FAST, ADS, D-CAN, ENET), KWP-мира (KWP2000/KWP FAST/ISO9141/ISO14230/KWP1281/KW71), UDS/ISO-TP/DoIP, TP2.0, J2534 Pass-Thru и любых самодельных OEM-протоколов.

## Правило номер ноль: сначала лог, потом теории

Никогда не строишь спецификацию «по памяти» или по интернету, пока то же самое не подтверждено живым логом. Каждое утверждение в спецификации помечай статусом:

- `wire-verified` — подтверждено логом с живого ЭБУ (а для записи — побайтовым чтением назад);
- `code-grounded` — извлечено из кода/трасс оригинальной программы (строки, дизасм, литеральный каталог);
- `hypothesis` — предположение, требует эксперимента.

Смешение этих уровней — главный источник сожжённых блоков и потерянных недель.

## Маршрут: 8 фаз

| Фаза | Что делаем | Куда смотреть |
|---|---|---|
| 0 | Опознание: кто, чем, как, что уже есть | этот файл, `protocol-reference` (таблица сигнатур) |
| 1 | План захвата: слой перехвата, стенд, бэкапы | `deep-log-capture` |
| 2 | Захват логов (пассивный и/или активный) | `deep-log-capture` |
| 3 | Декод: кадры, чексуммы, сервисы, тайминги | `log-analysis` |
| 4 | Спецификация с пометками статусов | `protocol-reference` (шаблон протокола) |
| 5 | Реплика: транспорт, клиент, инструмент | `protocol-replica-build` |
| 6 | Wire-верификация (read-only → запись) | `protocol-replica-build` (acceptance) |
| 7 | Восстановление и безопасность | `protocol-replica-build` (recovery) |

Не перескакивай через фазы. Типичная ошибка — начать писать код клиента на фазе 3 «пока и так понятно»: тогда фаза 6 превращается в отладку по догадкам.

### Фаза 0 — Опознание (30 минут, которые экономят дни)

Собери факты, прежде чем что-то писать:

1. **Что за блок и машина.** Модель ЭБУ, поколение, VIN/софт. Для BMW: E-серия → скорее DS2/K-line; F/G-серия → D-CAN/ENET + UDS.
2. **Какая программа умеет то, что нужно снять.** Название, версия, путь, какое железо использует. BMW-инструменты (INPA/WinKFP/Tool32, NFS) уже умеют писать трассы — это самый дешёвый источник (см. `protocol-reference/references/ediabas.md`).
3. **Железо стенда.** FT232/FT2232 (K-line), K+DCAN, J2534-адаптер, ENET-кабель. Проверь драйвер (D2XX или VCP — взаимоисключающие!) и серийник адаптера.
4. **Что уже есть в проекте.** Трассы (`work/orig-capture/`), старые логи, спецификации, дизасм, образы прошивок, чтения идентификации.
5. **Есть ли стенд на столе.** Запись/стирание — только на стендовом ЭБУ (питание 12В, K-line, масса). Для машин — только чтение, если владелец явно не разрешил запись.

Быстрая сигнатура протокола (детали и байтовые примеры — в `protocol-reference`):

| Признак | DS2 (BMW) | KWP2000 5-baud | KWP2000 fast | ISO 9141-2 | KWP1281 | UDS (CAN) |
|---|---|---|---|---|---|---|
| Линия | K 9600 8E1 | K/L 10.4k 8N1 | K 10.4k 8N1 | K/L 10.4k 8N1 | K 10.4k | CAN 500k |
| Инит | просто открыть порт | 5 бод, адрес 0x33 | K低25мс+K高25мс | 5 бод 0x33 | 5 бод | — |
| Кадр | `12 <len> … <xor>` | `fmt tgt src … cks` | `fmt tgt src … cks` | `68 6A F1 … cks` | `0x55 0x01`, блоки | ISO-TP: `02 01 0C …` |
| Cks | XOR всех байт | сумма mod 256 | сумма mod 256 | сумма mod 256 | XOR блока | CAN CRC |

Результат фазы — файл `01-recon/recon.md`: гипотезы и что проверяем следующим.

### Фаза 1 — План захвата

Выбери слой перехвата (полная таблица уровней — в `deep-log-capture`):

- **Своя программа должна уметь ЭТО же** → пиши активный клиент/логгер (D2XX напрямую, `ftdi_kline_logger.py`).
- **Снять обмен ЧУЖОЙ программы** → по возрастанию «глубины»: штатные трассы программы (EDIABAS `ifh.trc`) → API-хуки (Frida на serial), → прокси-DLL драйвера (`FTD2XX.DLL`, J2534) → USBPcap/логический анализатор.
- **Понять тайминги физики** (5-baud init, паузы, битые фронты) → логический анализатор (два канала: K-линия и RX трансивера).

Обязательные подготовки: бэкап содержимого ЭБУ через существующий инструмент; схема питания стенда; план «если сессия упадёт» (какой программой восстанавливаем, есть ли pending-состояния).

### Фаза 2 — Захват

Канон записи лога — `deep-log-capture/references/log-format.md`. Минимум, который обязан быть в логе: шапка с конфигурацией (порт/адаптер/скорость/чётность/latency, версия софта, дата), монотонные таймстампы + якорь wall-clock, направление, сырые байты, отметка эха, ошибки (framing/overrun). Не парси на этапе захвата — парси потом, из неизменяемого файла.

Для аудита чужих программ: сохрани ОБА лога — «золотую трассу» поминутного обмена и контекст (какие кнопки жали, что показывала программа, `app-state-*.png`).

### Фаза 3 — Декод

Скилл `log-analysis` + скрипты. Минимум на выходе:
- `decoded-telegrams.txt` — каждый кадр: номер, тайминг, направление, байты, декод полей;
- таблица «сервис → запрос → ответ → семантика»;
- модель таймингов (кто кого ждёт, таймауты, паузы, «мёртвые окна»);
- список аномалий и вопросов.

### Фаза 4 — Спецификация

Пиши по шаблону `protocol-reference/references/TEMPLATE-protocol.md`. Обязательные разделы: физический уровень; инициализация; кадр (поля, длина, чексумма — с алгоритмом и эталонными байтовыми примерами, проверяемыми вручную); адресация; таблица сервисов; тайминги; сессионная машина (включая состояния отказа/pending); безопасность (авторизации, seed/key); программирование (erase/write/finalize/commit, размеры блоков, CRC регионов); открытые вопросы.

Каждый эталонный пример кадра снабжай его чексуммой, посчитанной инструментом, — чтобы по спецификации можно было написать юнит-тест.

### Фаза 5 — Реплика

Скилл `protocol-replica-build`: транспорт-абстракция, клиент протокола, инструмент (probe/flash), симулятор для офлайн-тестов, строгий ACK и ретраи, гейты стирания/записи.

### Фаза 6 — Wire-верификация

Порядок строго от безопасного к опасному:
1. read-only: идентификация, чтения памяти, DTC — сверка с оригиналом бит-в-бит;
2. идемпотентные записи в ЗАТЁРТУЮ область (0xFF) с чтением назад;
3. полный цикл с бэкапом и восстановлением;
4. acceptance-лог с результатом (например, sha256 образа) — сохраняется в проект.

### Фаза 7 — Recovery и безопасность

Заранее знай ответы: как выйти из pending-состояния (не всегда спасает цикл питания — у BMS46 спасает только завершённый прогон WinKFP), как восстановить прошивку, что «одноразового» есть в сессии (у BMS46 стирание доступно только в свежем цикле питания). Никогда не пиши на машине без явного «да» владельца.

## Конвенции проекта (переносимы между задачами)

Структура каталогов, проверенная на реальном RE-проекте:

```
00-original/          оригинальные файлы (EXE, дампы, архивы) — только чтение
01-recon/             recon.md, спецификация протокола, трассы (traces/), decoded-telegrams.txt
02-decompiled/        дизасм/декомпиляция (если нужно)
03-resources/ 04-metadata/ 05-spec/    материалы и спецификации
10-replica/           наша реализация (src/, tools/, tests/, docs/)
work/orig-capture/    захваты обмена, скрипты анализа, «золотые трассы»
work/handoff/         память для следующей сессии
```

Имена артефактов: `winkfp-session-trace.txt` (золотая трасса), `ACCEPTANCE-*.log` (приёмка на железе), `replay-*.log` (наши прогоны), `*-verified.md` (спецификации с wire-подтверждением).

## Подключение соседних скиллов

- Захват/логгеры/прокси → `deep-log-capture`
- Декод и анализ логов → `log-analysis`
- Протоколы, EDIABAS, шаблон спецификации → `protocol-reference`
- Реализация и приёмка → `protocol-replica-build`

## Эталонный кейс для образца

Полный цикл «обратный инжиниринг + прошивка чужого образа» на BMW BMS46 (DS2/K-line, FT232R): разбор в `protocol-replica-build/references/playbook-bms46.md`. Если задача похожа — начни с него, там зафиксированы все грабли: эхо, лестница скоростей, «мёртвое окно» после старта сессии, CRC калибровок, pending-состояние.
