# Методика разбора протокола (разобранный кейс: BMS46 / BMW DS2)

Кейс: неизвестный (частично) протокол Bosch BMS46 (DME M43, E36/E46), дилерский флешер WinKFP + самописное приложение. За 2 сессии: снятие «золотой» трассы, разбор flash-сессии на 2173 обмена, доказанная прошивка чужого образа, восстановление из pending. Ниже — воспроизводимая методика с конкретными ходами.

## 1. Порядок действий, который сработал

1. **Найти штатный источник трасс.** EDIABAS пишет `ifh.trc` (байтовый обмен, мс-метки) и `api.trc` (джобы). Это дало эталонные обмены с первого дня — включая ID, чтения памяти, DTC.
2. **Определить кадр по первому же обмену.** В трассе видно: запрос `12 04 00 16`, ответ `12 2E A0 … 9F`. Проверка XOR (0x12^0x04^0x00=0x16) и пары длина/фактическая длина вскрыла формат: `[addr][полная длина][payload][xor]`.
3. **Собрать собственный клиент-зонд** (HwProbe raw): отправка произвольных телеграмм, приём с эхо-обработкой, логирование. С этого момента каждый вопрос к ЭБУ — эксперимент, а не догадка.
4. **Снять полную сессию чужого ПО** на байтовом уровне. Способ: Frida-хук COM-порта (VCP) — программа ходит через COM6. Получили 27 557 строк, разобрали 2173 обмена.
5. **Разложить сессию на этапы** по кадрам: prep / auth / enter / writes / ctl / final / commit. Каждый этап — отдельная гипотеза с проверкой на живом блоке (raw-прогон).
6. **Проверить гипотезы на живом ЭБУ** по одной (без записи данных): авторизации, окно, вход — и сравнить ответы.
7. **Воспроизвести полный цикл** (реплей золотой трассы с подстановкой своего образа калибровок) с чёткими критериями успеха — и добиться побайтового совпадения после чтения назад.
8. **Разобрать прошивку** (дизасм 68k) для объяснения найденного: обработчики `07`, таблица регионов, CRC, статусы.

## 2. Конкретные находки и как их получили

### 2.1 Формат и статусы
- Формат: `[addr][len(полный)][payload][xor]`, 9600 8E1, эхо обязательно.
- Статус = payload[0]: `A0` OK/данные, `A1` busy, `A2` принято-запись, `B0` отказ. Статусы выведены из комбинации: трассы EDIABAS + строки оригинального ПО («Response 0xB0 - Read blocked by ECU») + эксперименты.

### 2.2 Двузначные команды (важнейший урок)
`04 05` standalone = очистка ошибок; `04 05` ВНУТРИ сессии чтения страниц (`04 00`, `04 01`…) = продолжение страницы. **Контекст меняет семантику.** Всегда проверяй команду в обоих контекстах, прежде чем писать в спецификацию.

### 2.3 Тайминги: «мёртвое окно»
После `07 06` (старт программирующей сессии) ЭБУ стирает целевой блок: программа ~3 с, калибровки ~0.8 с. В это окно он **не отвечает**, а присланные телеграммы эхо возвращает — парсер, принимающий «любой не-эхо кадр» за ответ, молча терял целые блоки (симптом: слоты версий остались FF → финальная валидация `0D`). Лечение: ждать полный maxWait (9 с для `07 0F/07 06`), не выходить по «idle».

### 2.4 Строгий ACK
Запись блока `07 02 <addr24> <len8> <data>` подтверждается ответом, содержащим ТЕ ЖЕ addr24/len. Иначе отложенный ответ на предыдущую телеграмму принимается за ACK — и сессия портится. Ретраи (4 попытки) безопасны: записи идемпотентны; после 4 неудач — ABORT.

### 2.5 Целостность образа
- Таблица CRC-16 (отражённая, init=0) найдена в образе по 0x3D20 (256 слов BE).
- **Цепочка регионов**: таблица @0x14204 (16-байтные записи: +2 маска, +4 start, +8 end, +12 указатель на адрес записи cks); init каждого следующего региона — CRC предыдущего.
- Калибровки `[0x8040..0xFFF9]`, слово CRC на 0xFFFA. Эталоны: завод `2989`, обновление `E0C8`, AKPP `8893`.
- Проверка: скрипт `crc_verify.py` (пересчёт и сверка). Правка калибровок без пересчёта CRC → отказ финальной валидации (`0D`/`04`).

### 2.6 Flash-сессия (итог разбора золотой трассы, 2173 обмена)
Этапы и ключевые телеграммы — в `protocol-reference/references/ds2-bmw.md` §5. Особенности: две BMW-авторизации (`90 42 4D 57 04`, `90 9A 9B 9C A3`, затем `90 42 4D 57 07`), вход `07 0F 00 00 00 00` (без авторизации → `A2`!), старт `07 06 …` с паузой на стирание, запись `07 02 <конец блока>`, контрольное слово `07 02 03 FF FC 04 55 FF AA 00`, финал `07 0F 03 00 00 00`, коммит `0A` до `A0 00`.

### 2.7 Дизасм прошивки (когда нужно объяснение, а не только протокол)
- `cmd 07` → handler 0x22E8; таблица субфункций @0x23DE: `02`=запись, `06`=старт сессии, `0F`=валидация.
- Статусы `07 0F` — цепочка проверок (первый не прошедший = код ответа): версии/ID (0x3FE6 + магия 5AA5@0x3FFE), AIF-блоки (0x3FCB0), кросс-сравнение, маркер `55FFFFFF`@0x3FFC, слоты версий, контрольное слово калибровок @0xFFFC, кросс-сравнение 0x8010↔0x3FCB0, `1` = всё ОК.
- `0A` = коммит: прогон таблицы регионов 0x14204 с CRC-16; статус = AND масок (6&5&5&3=0 = все прошли; `04` = калибровка не прошла).

### 2.8 Каталог телеграмм в EXE
В теле флешера найден литеральный каталог (EXE 0x2A0–0x557, 23 записи), все XOR сходились; содержит уже известные телеграммы (`12 04 00 16`, `0B 03`, `43 FF FF`, `05`) — кросс-валидация каталога и протокола. Это стандартный приём: программы хранят шаблоны рядом (`mine_telegrams.py`).

## 3. Реконструкция состояния (pending и восстановление)

- Признаки pending: AIF `00 37 3A` вместо `01 45 9A`, ID с дырками FF, `A2` на авторизацию записи.
- Цикл питания НЕ лечит (маркер во флеше). Лечение — завершённый прогон штатного WinKFP. После него — работать «в том же цикле питания», если предстоит своя сессия.
- Урок для любых ЭБУ: **всегда документируй состояние восстановления ДО записи** и проверяй, что оно доступно на стенде.

## 4. Анти-паттерны анализа (все встречались в реальности)

1. Принимать любой не-эхо кадр за ответ (см. 2.3) — потеря блоков.
2. Считать чексумму по «похожему» алгоритму без проверки на всём корпусе (KWP1281 вовсе без XOR; DS2 — XOR без последнего байта; KWP2000/9141 — сумма).
3. Верить одному кадру из интернета (кадр `80 F1 10 81 C1 EA 8F` — невалиден; `81 10 F1 81 05` — с неверной CS).
4. Забыть про эхо при подсчёте таймингов запрос→ответ.
5. Игнорировать контекст двузначных команд (2.2).
6. Писать в ЭБУ до того, как прочитан бэкап и известен путь восстановления.
7. Доверять таймингам FTDI на уровне «микросекунды» (реальность: latency 1 мс + USB-фрейм).

## 5. Чек-лист завершённости разбора

- [ ] Кадры нарезаются на 100% корпуса (нет «остатков»).
- [ ] Чексумма валидна на 100% кадров (или объяснено, почему нет).
- [ ] Каждой операции сопоставлен запрос/ответ и подтверждение (лог + строка программы).
- [ ] Тайминги: таблицы переходов + известные «мёртвые окна» + busy-статусы.
- [ ] Состояния восстановления описаны и проверены.
- [ ] В спецификации нет утверждений без статуса.
