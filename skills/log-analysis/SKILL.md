# Анализ логов обмена с ЭБУ

Цель — превратить сырой лог в **доказуемые** артефакты: список кадров, каталог сервисов, тайминги, сессионная машина, кандидаты спецификации. Обратный инжинир — это в первую очередь работа с корпусом логов: гипотезы проверяются на ВСЁМ корпусе, а не на одном кадре.

## Пайплайн

### 1. Нормализация
Привести лог к канону (`../deep-log-capture/references/log-format.md`) — парсер понимает диалекты: HwProbe, Frida (`[+t] TX ftd2xx …`), EDIABAS (`_STD INPUT: …`), произвольные hex-строки.
`python scripts/telegram_parse.py --format auto < log.txt`

### 2. Framing — как режутся кадры
Три модели, бери ту, что объясняет ВЕСЬ корпус:
- **по полю длины в кадре** (DS2: второй байт = полная длина; KWP2000: FMT/байт длины);
- **по таймауту между байтами** (ISO 9141-2, KWP1281-подобные; важно не «склеивать» быстрые пачки);
- **фиксированные блоки** (редко).

`telegram_parse.py --framing ds2|kwp|gap:ms|line` — на выходе нумерованные кадры с Δt, направлением и валидностью чексуммы.

### 3. Чексумма
Не угадывай по одному кадру: `python scripts/checksum_solver.py --file log.txt` прогоняет модели (XOR8, сумма mod 256, инверсии/дополнения, CRC8 по 4 полиномам × init × отражение, CRC16 CCITT/XMODEM/MODBUS/отражённый KWP-стиль) по всем кадрам и показывает, какие сходятся на всём корпусе. Табличные CRC (как у BMS46) solver не найдёт — только дизасм/образ (см. методичку).

### 4. Каталог команд и семантика
- Частотный анализ: какие payload’ы встречаются, с какой стороны, с какой периодичностью.
- **Корреляция с действиями**: кадр(ы), уникально появившиеся после нажатия «стереть ошибки», и есть код очистки (у BMS46: `05`; ID появляется после клика «читать» → `00`).
- **Корреляция со строками ПО**: «Response 0xB0 - Read blocked by ECU» объясняет обработку `B0`; ошибка «Unable to erase flash» привязана к телеграмме — смотри рядом с местом использования строки в дизасме.
- **Майнинг литеральных каталогов**: программы хранят шаблоны телеграмм рядом: `python scripts/mine_telegrams.py --file app.exe --addr 0x12` — ищет `[addr][len][payload][xor]` с валидными XOR (у BMS46 так извлекли каталог из 23 записей и кросс-валидировали по известным командам).

### 5. Тайминги и «мёртвые окна»
Строй таблицу Δt для каждого типа перехода (запрос→ответ, ответ→следующий запрос). Найденные феномены:
- ответы приходят не сразу (erase ~3 с — телеграммы в это окно эхо возвращают, но НЕ обрабатываются);
- busy-статусы (`A1`/`0x21`) вместо ответа — это «повтори позже», а не ошибка;
- предупреждение о таймауте в логе ≠ ошибка протокола: ранний выход по idle — классический баг парсера/клиента.

### 6. Сессионная машина и состояния
Собери граф: какие последовательности включают/выключают режимы; как выглядит отказ; как выглядит «pending» (у BMS46: AIF `01 45 9A` ↔ `00 37 3A` + `A2` на авторизацию). Пометь одноразовые операции (стирание доступно только в свежем цикле питания).

## Методики (в порядке силы доказательства)

1. **Дифференциальный эксперимент на стенде**: меняем одну переменную (адрес, длину, значение) — смотрим, что меняется в ответе. Самый быстрый способ понять семантику полей (у BMS46 так подтвердили запись блока 0x40 и игнор 0x60).
2. **Реплей с вариацией**: воспроизвести сессию до точки X, повторить X×N с разницей — для таймингов и повторов.
3. **Дизасм обработчиков**: для своих ЭБУ — найти таблицу субфункций (у BMS46: `07` → handler 0x22E8, таблица @0x23DE: `02`=запись, `06`=старт сессии, `0F`=валидация) и читать коды статусов из кода.
4. **Проверка целостности образов**: найти таблицу CRC (0x3D20), регионы (таблица @0x14204), пересчитать (`work/orig-capture/crc_verify.py` в эталонном проекте).
5. **Каталог строк EXE** (быстрые подсказки о поведении: «Non 0xA0 response attepting to set 19200 baud»).

## Выходные артефакты (обязательные)

- `decoded-telegrams.txt` — все кадры: номер, Δt, направление, байты, декод полей, валидность CKS.
- Таблица «операция → запрос → ответ → статус подтверждения → ссылка на строку лога».
- Модель таймингов (таблица переходов + аномалии).
- Список открытых вопросов с планом проверки на стенде.

## Правила доказательности

- Каждое утверждение спецификации — с байтовым примером ИЗ ЛОГА и ссылкой на файл:строку.
- Отличай «ответ ЭБУ» от «эха адаптера» и от «повтора тестера» — иначе посчитаешь тайминги неверно.
- Один кадр — это анекдот, а не закономерность: проверяй на всём корпусе (`--selftest` в скриптах — быстрая проверка логики парсера).
- Противоречия в источниках фиксируй в спецификации отдельным списком (пример — расхождения W1/P2 в KWP2000).
